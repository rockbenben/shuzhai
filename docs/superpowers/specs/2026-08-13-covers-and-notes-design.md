## 背景

`AGENTS.md` 的「还没做的」清单列了三项：应用图标、封面、划线/笔记。**核实后其中两项是过时的**：

- **应用图标**已经接上了——`build/icon.png` 存在（8.8KB），`electron-builder.yml` 的 `buildResources: build` 指过去了。
  （只核实了配置，没有重新打包验证成品图标真的换掉了默认图标；清单该改成「待验证」而不是「没做」。）
- **划线/笔记**核心和界面都有：`highlight.ts` 六个函数、六个 rpc、阅读器里选中划线／点击取消／写笔记全通。真正缺的是**回看**——`highlight.notes` 这个 rpc 写好了但界面上没有任何地方调它，划完的线找不回来。而回看面板恰恰是 spec §5.1 明文要求的（「可在笔记面板中汇总查看」），所以这不是新需求，是补欠账。
- **封面**核心和 rpc 都有（`cover.ts` + `cover.get/set/clear`），`BookEditor` 里能手动选图。缺的是**批量来源**。

真实库的状态（8172 本）：0 封面、0 标签、0 分类、0 智能书架、0 划线。功能齐全，一条数据没用起来。

本设计解决两件独立的事：**封面的来源**和**划线的回看**。

## 一、封面抓取

### 已经量过的事实

这些数字决定了整个设计，不是估计：

**本地没有现成图片。** 扫了库里全部 15 个目录 / 8172 个 txt，**图片文件 0 个**。「用同名图片当封面」这条路在这个库上是空的。

**本地元数据够干净。** 书名作者都干净到「有可能精确匹配」的有 **7814 本（95.6%）**。拦在本地这侧的只有约 360 本：171 本书名带括号别名、101 本作者含多位数字（其中不少是真笔名如「Dr陈01」「38大虾」）、49 本没作者。

**普通 HTTP 够不到主流站点。** 起点返回 202 空响应（209 字节）、纵横 404、番茄 404。豆瓣、刺猬猫、塔读返回 200，但书名只出现在 `<title>` 和 meta 里——**搜索结果是 JS 渲染的**，初始 HTML 里没有数据。

**浏览器能拿到，命中率量出来了。** 同一批 10 本真实书目：

| 源 | 精确命中 | 说明 |
|---|---|---|
| 起点（浏览器） | **6–7 / 10** | 提取到书名、作者、封面 URL、书页链接 |
| 豆瓣（普通 HTTP） | **2 / 10** | 只对有实体出版的书有效 |

**首条结果几乎总是错书**，这是最重要的一条：搜「官仙」，起点首条给《重置世界：从女儿被夺舍开始》，豆瓣给《宋代文官官衔研究》；搜「武炼巅峰」（莫默），豆瓣给的是繁体台版《武煉巔峰》、作者「風飄絮」。**给错封面比没封面更坏**——看起来一切正常，但那是另一本书。已有的 `isExactMatch`（书名和作者都要精确一致，本地没作者直接判不匹配）把这些全部正确拒绝。

**封面 URL 在 `data-original` 而不是 `src`。** 起点搜索页的图是懒加载的，`src` 取到的是 `default_book.png` 占位图。不注意这一条，抓下来的会是 8000 张一模一样的占位图，**而且界面上看起来一切正常**。

### 架构

```
主进程
 └─ src/main/cover-fetcher.ts        ← 新增，唯一碰 Electron API 的地方
     ├─ 一个复用的隐藏 BrowserWindow（show: false）
     ├─ loadURL(搜索页) → executeJavaScript(提取脚本) → 候选数组
     ├─ 候选 → isExactMatch（已有）
     └─ 命中 → downloadCover（已有）→ setCover（已有）

src/core/cover-source.ts             ← 新增，纯函数，node:test 能直接跑
     ├─ QIDIAN / DOUBAN 的 SourceConfig（搜索 URL、提取脚本常量、字段映射）
     ├─ parseCandidates(html) → Candidate[]
     ├─ matchWithAliases(local, candidates) → 命中或 null
     └─ validateCoverBytes(buf) → 是不是真图片、是不是占位图
```

**为什么提取逻辑放 core**：`src/core/` 现在一个 electron import 都没有，那是它能用 `node:test` 直接跑的原因。只有「开窗口、加载、执行脚本」这层放 main。

**隐藏窗口共享一个、串行复用**，不是每本新建——建窗口开销 200ms+，而且本来就要串行限速。

**豆瓣作为兜底**：起点没命中时用普通 HTTP 查一次（不需要浏览器），同一套匹配判据。实测 10 本里补 1 本左右。

### 后台任务

**状态落库，不放内存。** 8172 本要跑几小时，中间必然关应用；「这本试过没匹配上」必须记住，否则每次重启都从头再撞同样的 8000 次网络请求。

迁移 15：

```sql
create table cover_fetch(
  book_id integer primary key references book(id) on delete cascade,
  status  text not null,        -- ok / nomatch / failed
  source  text,                 -- qidian / douban
  error   text,
  tried_at text not null default (datetime('now'))
);
```

这张表**是可再生的**（删了重抓一遍就有），不受铁律 3 约束。

**队列就是一条 SQL，没有游标要维护**：

```sql
select b.id from book b
 left join cover_fetch cf on cf.book_id = b.id
 where b.cover_path is null and cf.book_id is null
 order by b.id limit 1
```

关掉应用再打开，这条查询自然接着上次的位置。**没有「进度」这个状态要存，也就没有它和现实脱节的可能**——本轮已经修过两次「派生字段只写不还原」导致的自相矛盾记录，不再制造第三次。

**节奏与退避**：每本固定间隔 3 秒；429 或超时按 6s / 12s / 24s 退避；连续失败 5 次自动暂停并在界面说明原因。**不能默默地一直撞墙**——TTS 那次的教训是限流下的失败会被误读成「这个源不可用」，实际只是打太快（当时把 88 个能用的引擎误判成 52 个）。

**开关**在设置 →「书库」页：一个开关 + 一行进度（`已抓 N / 剩余 M / 没匹配上 K`）。关掉即停，下次打开接着跑。应用启动时若开关是开的，**延迟 30 秒再开始**，别和启动扫描抢资源。

**重试**：`nomatch` 不自动重试（站点没有就是没有），但给一个「重试没匹配上的 K 本」按钮——它**删掉那些 `nomatch` 行**，于是队列 SQL 自然把它们重新纳入。`failed`（网络错误）也归这个按钮管；`ok` 的不动。

### 安全阀

**这个应用现有的联网（死链探活、WebDAV、在线朗读、以后下载封面图）都只是「取数据字节」，
从不执行远程内容；隐藏窗口是第一次在应用进程里运行远程页面的 JS。** 这才是新增的攻击面，
所以下面的隔离一条都不能省。

窗口隔离：独立 `partition`（不和应用共享任何存储）、`nodeIntegration: false`、`contextIsolation: true`、拦掉 `window.open` 和新窗口、加载完立即 `stop()`。页面自己的 JS 必须跑（不跑没有渲染结果），但它够不到 Node、够不到库、cookie 不落到别处。**注入的提取脚本是写死的常量，不接受任何来自页面的代码。**

匹配三道：

1. `isExactMatch`（已有）——书名和作者都精确一致，本地没作者直接判不匹配
2. **别名也算数**——那 171 本《国产英雄(我的邻居是女妖)》，括号内外都试，任一精确命中即可
3. **下载的图要验**——三条：看文件头确认是真图片（不是看扩展名）；大小在 2KB–5MB 之间；**URL 里不含已知的占位图路径**（`images/common/default_book.png`）。
   主要防线是从 `data-original` 而不是 `src` 取地址，这三条是兜底——万一站点改了懒加载方式，尺寸下限也能挡住一部分。

**失败隔离**：单本失败只写一行 `failed`，不中断队列。

**隐私**：抓取会把**书名和作者**发到起点和豆瓣，这是拿到封面的必然代价。除此之外不发任何东西——不发文件路径、不发阅读进度、不发库的规模。

## 二、划线笔记的回看

阅读器工具栏加一个「划线」按钮，开一个面板：

- **本书**：按章节顺序列出划过的句子和笔记，点一条**跳到那一章的那个位置**（章内定位靠本轮刚做的 `char_offset`）
- **全库**：`highlight.notes` 不传 bookId 就是全部，按书分组
- 每条能改笔记、删划线（`highlight.setNote` / `highlight.remove` 都有）

写笔记现在用的是 `prompt()`，换成正常输入框。

**不做导出。** 现在 0 条划线，先让它能用起来；真需要导出，`export.ts` 加一个格式即可。

## 三、测试

**纯函数进 core，`node:test` 直接跑**：

- `parseCandidates` 喂一份存档的起点搜索页 HTML fixture
- `matchWithAliases` 的别名分支（括号内外都试）
- `validateCoverBytes`：占位图必须被拒、非图片必须被拒、超大必须被拒
- 队列 SQL：抓过的不重复出、`nomatch` 的不自动重试

**隐藏窗口测不了**，靠对着真站点跑验证脚本。**验证脚本要留在仓库里**，站点改版时能立刻定位是哪个选择器失效。

**回归守卫**：真实起点搜索页存一份 HTML fixture 进测试。站点改版时这条会先红，比「用户发现封面全是占位图」早得多。

## 不做的

- **不做全库一次性同步抓取**（8172 本 × 2–3 秒 ≈ 6 小时且会被限流），只做可暂停可续的后台任务
- **不做保底生成图**——用户明确要真封面；抓不到的保持现有占位色块
- **不内置番茄/纵横**——实测都是 404
- **不做划线导出**

## 风险

| 风险 | 应对 |
|---|---|
| 站点改版，选择器失效 | HTML fixture 回归测试先红；验证脚本留仓库里 |
| 抓到错书的封面 | 书名+作者双精确匹配，没作者直接拒 |
| 限流被误判成源不可用 | 指数退避 + 连续失败 5 次暂停并说明原因 |
| 命中率只有六成 | 已和用户确认接受；抓不到的保持占位 |
| 隐藏窗口加载远程内容 | 独立 partition、无 Node、拦弹窗、注入脚本是写死常量 |
